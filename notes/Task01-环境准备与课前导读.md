## 先给三句话结论

1. 这门课从头到尾只讲一件事：**AI 产品能有多强，取决于你喂给它什么数据，模型只是一个放大器。**
2. F0 那个「越用越好用」的例子，靠的不是模型升级，而是把每次聊天的经验写进了几个 md 文件里。
3. F1、F2 把这件事说成两个公式：`能力上限 = 数据质量 × 模型能力`，再往后是 `= 模型能力 × 数据质量 + 流程编排`。RAG、MCP、Skill、Memory 这四个热词，说白了都在回答同一个问题：**什么数据、在什么时间、放进模型的上下文里**。

## 二、环境准备：把「能不能跑」拆成四道关卡

以前配环境的老毛病是「照抄命令，报错就猜」。这次我改成一道一道过：每过一关就验证一次，错在哪立刻知道。

| 关卡 | 怎么验证 | 不过关会怎样 |
| --- | --- | --- |
| ① Python 和虚拟环境 | `python --version`、`pip check` | 包装上了但 import 就报错 |
| ② 依赖装全了没 | `python -m pip check` | 运行时提示缺包、版本打架 |
| ③ 离线自检脚本 | `python code/D3/d3_5_evaluate.py` | 这个不用 Key 也能跑，跑不动说明 ①② 有问题 |
| ④ 模型 Key 和数据层 | 真实接口脚本、`code/check_seekdb_env.py` | 401 / 403 / 连不上 |

### 2.1 版本：教程用 3.11，我机器上是 3.13

教程的自动测试固定用 **Python 3.11**，`pyseekdb` 和 X2 章节要求 **3.11 以上**（教程原话）。

我这台机器实测：

```text
Python 3.13.11   (D:\python\python.exe)
Node   v24.16.0
Docker 没装
```

我的理解：3.13 确实满足「3.11 以上」，但这类教学仓库用的 `langchain`、`ragas`、`pyseekdb` 都还在快速更新，新版本 Python 常常还没有现成的安装包（wheel），装起来容易卡住。**更稳的办法是单独建一个 3.11 的虚拟环境**，别去动全局 Python。

### 2.2 Windows 上的命令（教程原话，在仓库根目录执行）

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -r code/requirements-test.txt
python -m pip check
$env:PYTHONPATH = "code/D3;code"
python code/D3/d3_5_evaluate.py
```

两个小体会：

- `$env:PYTHONPATH = "code/D3;code"` 是 Windows 写法，路径之间用**分号**；Linux / macOS 用冒号。教程给了两套，别抄错。
- 最后那条 `d3_5_evaluate.py` 是**整门课唯一一个「不用 Key、不用数据库」的自检脚本**，结果会写到 `code/D3/reports/`。先把它跑通，再去配 Key，这样「环境问题」和「账号问题」就不会混在一起。

### 2.3 依赖和 `.env` 配置

`code/requirements.txt` 里的关键版本（教程原话）：`langchain>=1.2.15`、`langchain-openai>=1.1.12`、`langchain-core>=1.2.27,<2`、`openai>=1.0.0`、`langgraph>=1.1.6`、`pyseekdb>=1.2.0.post1`、`ragas>=0.2.0,<0.3`、`mcp[cli]>=1.28.1,<2`（注释里说 2.0 把 FastMCP 的兼容入口删了）、`python-dotenv`、`PyYAML`、`datasets`。

配置从 `code/.env.example` 复制一份改名 `.env`，主要填这几项：

```text
SILICONFLOW_API_KEY / SILICONFLOW_BASE_URL=https://api.siliconflow.cn/v1
DASHSCOPE_API_KEY   / DASHSCOPE_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
RAGAS_API_KEY / RAGAS_BASE_URL            # 可以不填，会自动用 SiliconFlow 的
RAGAS_LLM_MODEL=deepseek-ai/DeepSeek-V3
RAGAS_EMBEDDING_MODEL=BAAI/bge-m3
```

读取顺序（教程原话）：先看 `code/.env`，再看上一层的 `.env`，**但系统环境变量优先级最高，`.env` 覆盖不了它**。这条特别坑：如果你以前在系统里设过同名变量（哪怕值是空的），`.env` 写了也不生效，表现就是「Key 明明填了却报 401」。

Key 从哪来，教程给了两个渠道：阿里云百炼（福利页可以领 1 亿 Token 额度）、硅基流动（专属链接注册并实名送 16 元券，教程原话说「够跑通全部示例」）。

### 2.4 数据层：seekdb 和 Docker

D1 前半段和 D3 的离线评测**不需要**数据库；从 D1 后半段、D2 开始才需要 seekdb。

Windows 上有个硬限制（教程原话）：**不能用 Embedded 模式**（缺 `pylibseekdb` 这个原生扩展），必须用 Docker 起一个服务：

```powershell
docker compose -f code/docker-compose.yml up -d
docker compose -f code/docker-compose.yml exec -T seekdb mysql -h127.0.0.1 -P2881 -uroot -e "SELECT 1;"
$env:SEEKDB_MODE="server"; $env:SEEKDB_HOST="127.0.0.1"; $env:SEEKDB_PORT="2881"
$env:SEEKDB_DATABASE="easy_data_x_ai_demo"; $env:SEEKDB_ALLOW_DESTRUCTIVE="1"
python code/check_seekdb_env.py
```

我的实际情况：机器上没装 Docker。这不影响 Task01 打卡（这周的验收点只到「离线评测能跑」），但意味着**学 D2 之前必须把 Docker 装好**，不然会卡住。我把它记成了待办，而不是等报错再回头补。

两个已知的坑（教程原话）：

- `code/docker-compose.yml` 和 `code/X2/docker-compose.yml` 都用 `2881/2886` 端口，只能挑一个开，别同时起。
- `SEEKDB_ALLOW_DESTRUCTIVE=1` 只能给演示库/测试库用；测试库得先 `CREATE DATABASE`，只改库名不会自动建库。

### 2.5 常见报错怎么办（整理自教程 FAQ）

| 看到什么 | 大概率是什么原因 | 怎么办 |
| --- | --- | --- |
| 401 / authentication failed | Key 没读进来，或被系统环境变量盖掉了 | 检查 `.env` 放的位置，检查同名系统变量 |
| 403 / model permission | 账号没开通这个模型 | 去控制台开通，或换个模型 |
| 429 | 请求太频繁被限流 | 降低并发，加个退避重试 |
| model not found | 把控制台里的「中文展示名」当成接口的 `model` 参数了 | 用模型 ID |
| MCP 报缺依赖 | 启动 MCP 的 Python 和装依赖的 Python 不是同一个 | `python -m pip check`，统一解释器 |

还有一句方法论（教程原话）：**离线测试和真实接口测试不能互相替代。** 离线跑通说明代码没问题，真实接口跑通才说明 Key 和额度没问题。

## 三、F0：为什么这个 AI「越用越好用」

F0 的结论很干脆：不是模型变聪明了，是**数据变多了**。教程原话说「OpenClaw 本身不生产智能，它只是让模型发挥更好的框架」。

### 3.1 三种典型用错的方式

| 现象 | 教程的解释 | 背后的道理 |
| --- | --- | --- |
| 什么都往一个 Agent 里塞 | 应该拆成多个 Agent，各自有自己的 `workspace` / `memory` / `session` | 经验分开攒，互不污染 |
| 觉得它「没被训练过」，回答很空 | 所谓「训练」就是往 workspace 里堆数据文件、沉淀套路 | 数据就是训练 |
| 抱怨效果差 | 模型没选对 | 框架只负责发挥，不负责变聪明 |

### 3.2 撑起它的七个文件

| 文件 | 干什么用 | 我的大白话 |
| --- | --- | --- |
| `SOUL.md` | 人格、语气、行为边界 | 「它是谁」 |
| `USER.md` | 用户画像（时区、习惯、技术偏好、说话风格） | 「我是谁」 |
| `AGENTS.md` | 行为规范 + 踩过的坑（教程原话：犯了错就写下来，让以后的自己别重犯） | 「上次错在哪」 |
| `TOOLS.md` | 环境备忘（SSH 主机、设备名、路径习惯） | 「工具怎么用」 |
| `SKILL.md × N` | 某类活的操作手册，内置 52 个 | 「这类活的标准流程」 |
| `memory/YYYY-MM-DD.md` | 按天记流水账，索引进 SQLite，支持全文和向量检索 | 「今天发生了什么」 |
| `MEMORY.md` | 从日记里提炼的长期结论，每次对话都会带进 prompt | 「长期记住的事」 |

### 3.3 两层循环

外层是**读写数据**：聊天前把一批 md 拼进 prompt，聊完让 Agent 把新学到的东西写回 md。
内层是**建索引**：日记进 SQLite 做全文 + 向量索引，解决「几百篇记忆塞不进上下文」的问题。

我的理解：第二层其实就是手工版的 RAG——「一堆 md + 一个索引 = 最小可用知识库」。教程没这么讲，但 F1 对 RAG 的定义（外部知识按需检索进上下文）跟这套机制是一回事，所以我更愿意把它看成 RAG 的一个工程特例，而不是另一个新概念。

### 3.4 四个推论

1. Agent 的价值在数据：把 workspace 拷走，能力就跟着走了；删掉，能力就归零。（教程倾向）
2. 调教 Agent ≈ 写数据：用大白话写 md 就行，不用先成为 prompt 高手。（教程倾向）
3. 两个 Agent 的差距，多数时候是数据的差距，不是模型的差距。（我的理解）
4. 「数据即知识」这个思路，能套用到几乎所有 Agent 产品设计上。（教程倾向）

教程自己也承认局限：md 全量加载会让上下文过载、token 烧得快；云上的 md 版本管理也不好做。这两条正好是后面 P3、D4「记忆系统」要解决的。

## 四、F1：大模型的三个天生短板

### 4.1 一个公式

教程原话：`AI 产品能力上限 = 数据质量 × 模型能力`。用乘号不用加号，意思是**缺一样就塌**：模型再强，数据是 0，结果还是 0。

### 4.2 三种局限，其实是同一个病根

| 毛病 | 长什么样 | 缺的是哪种数据 |
| --- | --- | --- |
| 幻觉 | 说得头头是道，但事实是错的 | 能验证的事实数据 |
| 知识截止 | 不知道最近发生的事 | 实时数据 |
| 回答太泛 | 说的都对，但跟你没关系 | 你的、你的业务的专属数据 |

### 4.3 幻觉为什么治不好

教程的推理是这样：训练学的是「什么样的文字组合在统计上更像人话」→ 生成时按概率**一个词一个词往下猜**→ 产出的是「听起来合理的话」，不是「查证过的答案」；模型**分不清自己是在「知道」还是在「猜」**。

最形象的例子是：问「天空是」，它答「蓝色」——因为它见过太多次「天空是蓝色」，可此刻窗外在下雨，天是灰的。它没有眼睛，只有语言统计。

所以「换个更强的模型」对这类问题基本没用：再聪明的猜词机器，遇到训练数据里没有的事实，还是只能猜。解法是**把数据给它、让它有据可查**——这就是 RAG 的起点。

### 4.4 Token 和上下文窗口

- Token 是模型处理的最小单位。教程口径：英文大约 **0.75 个词 = 1 个 Token**（`understanding` 会被切成 `under` + `standing`），中文大约 **1 个汉字 = 1～2 个 Token**，标点和空格也算钱。
- 上下文窗口就是「一次能看多少」。教程举的三档：GPT-4o **128K**（约 200 页）、Claude 4 Sonnet **200K**（约 300 页）、Gemini 2.5 Pro **1M**（约 1500 页），对比 GPT-3 时代的 4K，几年间扩大了约 **250 倍**。这是教程写作时的口径，不是实时规格。
- 关键一句（教程原话）：「上下文窗口的限制，是后面所有 AI 架构设计的根本原因」。窗口再大也是**一次性的**，新开一个对话就清空——所以大模型**天生没有记忆**。

我的理解：把「没有记忆」当成默认设定，很多设计就顺了——RAG 是把外部资料临时塞进窗口，Memory 是把历史沉淀下来按需塞回窗口，Agent 的多轮循环是在同一个窗口里反复自我纠错。它们抢的是同一块稀缺资源：上下文。

### 4.5 遇到「AI 答不好」时，按顺序问三个问题

1. 它缺的是哪种数据？事实、实时，还是跟你有关的数据？
2. 问题在模型层还是数据层？换个更强的模型能解决吗？
3. 这个数据补得上吗？——有但拿不到，就去搭检索；压根没有，就先做采集。**这是产品决策，不是技术决策。**

教程还给了一个当天就能做的实验：找一个 AI 答不好的问题，把正确答案直接贴进对话。它要是一下就答对了，说明卡的是数据，不是模型。

## 五、F2：Agent 到底是个啥，四个热词说白了

### 5.1 公式加了一项

`AI Agent 能力上限 = 模型能力 × 数据质量 + 流程编排`

前面乘法是地基，后面加法只是优化。教程的说法是：流程编排决定「怎么走」，`数据 × 模型`决定「能走多远」。编排做得再花，也超不过数据的边界。

### 5.2 Agent 是什么

教程引用 Lilian Weng 2023 年那篇《LLM Powered Autonomous Agents》的定义，四个零件：**大模型（大脑，负责推理和反思）+ 记忆 + 规划 + 用工具**。它的运行方式是**看一眼 → 想一想 → 做一步 → 看结果 → 再想**，是个循环，不是一问一答。

实际占比（教程原话数字）：**ReAct 式（边想边做）占 80%–90%**（LangChain 默认 Agent、OpenAI Function Calling、多数商业 Agent），**显式画流程图的占 10%–20%**（LangGraph、Dify 工作流、RPA+AI）。

这组数字纠正了我的一个偏见：我原以为上线产品都得先把流程图画好，实际上大部分 Agent 还是「边走边看」，编排主要用在流程固定、要求可复现的场景。

### 5.3 四个热词，本质都是数据

| 热词 | 听起来是什么 | 教程说的本质 |
| --- | --- | --- |
| RAG | 让 AI 去查资料 | 把知识数据检索进来 |
| MCP | 统一接工具 | 把数据接入这件事标准化 |
| Skill | 调用现成技能 | 把人的经验变成结构化数据 |
| Memory | 记住、会学习 | 把数据攒下来并能召回 |

拆开说：

- **RAG**：最简单的做法（Naive RAG）是固定流程「检索 → 拼进 prompt → 生成」，只查一次、不会随机应变；进阶做法（Agentic RAG）让 Agent 自己判断「要不要查、查哪儿、查几次」，能多轮查、多源对照、错了重来。上限由四件事决定：知识库本身的质量、怎么切分（块大小和重叠）、怎么检索（纯向量还是混合）、Embedding 选哪个模型。教程引了句业界话：「RAG 的 80% 问题都是数据问题，不是模型问题」。
- **MCP**：解决「M 个框架 × N 个工具」的集成地狱，统一成 Server / Client 之后变成 **M+N**；可以理解成「AI 工具生态里的 USB 接口」；三件事：调用工具、暴露资源、预设 prompt 模板。
- **Skill**：把人的专业经验写成结构化数据（操作步骤、行业规则、成功案例、术语表），本质是**把「怎么做」这件事显式写下来、可复用**。效果取决于写得多结构化、**找得到找不到**（几百个 skill 怎么检索出对的那个）、能不能复用。
- **Memory**（引 CoALA）：分三类——语义记忆（事实和偏好）、情景记忆（以前发生过什么）、工作/程序性记忆（行为规则）。效果取决于提炼得好不好、召回得准不准、**怎么忘**（过时信息怎么降权）。

关于 Skill 的「找得到」，我的理解：几百个 skill 里挑对那一个，本身也是一次检索——所以 Skill 系统的隐藏成本不在「写」，而在「建索引和召回」。教程原文只是抛了个问题，这个归因是我自己推的。

### 5.4 另一个好用的比喻

F0 里有个比喻挺好懂：单个 Agent 就像一个 Workspace；多个 Workspace 外面加一层 Gateway 做路由（微信消息进生活区，钉钉飞书进工作区），「OpenClaw 像操作系统，Agent 像应用程序」。

我的理解：这个比喻解释了为什么多 Agent 落地时，难的不是模型，而是**路由和边界**——跟操作系统要解决进程隔离、权限、调度，是同一类问题。

## 六、我自己的五条体会

以下是我读完后的个人判断，不是教程原文：

1. **「换模型」和「补数据」是两笔预算。** 问题在数据层时，升级模型的回报接近 0；先判断是哪一层，再决定钱往哪花。
2. **上下文窗口是这门课真正的稀缺资源。** RAG、Skill、Memory、Prompt 都在抢同一个窗口，区别只是「哪类数据、什么时候进来、占多少」。
3. **「记住」容易，「忘记」难。** 教程那句「让 AI 学会忘记，比让它记住更考验产品设计」很扎心——没有遗忘机制的 Memory，最后会变成一个越滚越大的垃圾堆。
4. **不该做 Agent 的场景就别硬做。** 产品篇给的三条判断（数据拿得到吗、任务说得清吗、失败扛得住吗）是个很好的否决清单，任一条不达标就别上自主 Agent。
5. **调教 Agent 的成果应该能进版本库。** 既然能力存在 workspace 的 md 里，那它就该进 Git、能 review、能回滚；否则「越用越好用」只是一次性的运气。
