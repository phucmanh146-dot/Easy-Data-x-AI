## 先给三句话结论

1. **做 Agent 之前先问一句「数据在哪」**——90% 的 AI 功能失败不是模型不行，而是立项时没人问这个问题。
2. P1 给了一把尺子：用「数据可得性、任务可定义性、流程编排」三个维度判断一个需求值不值得做 Agent，别上来就堆模型。
3. D1 把工程落地讲透了：对话的本质是一个消息列表，**Tool Use** 是模型从「只能说」变成「能做事」的分界线——模型负责判断，你的代码负责执行和拿数据。

## 二、P1：先判断值不值得做 Agent

### 2.1 开场故事：论坛小助手的弯路

课程作者讲了一个真实故事（教程原话出处：OceanBase 社区论坛）：

> 我在社区论坛做了个「论坛小助手」，用户发帖时默认 @ 它回答问题。上线后用户频繁抱怨「答非所问」。当时我以为是模型不行，就换成了当时最强的 GPT-4o。上线后，用户满意度几乎没有提升。

后来翻用户反馈才发现：**绝大多数答错不是模型理解错了，而是知识库里根本没有对应内容**——产品版本频繁更新，但知识库还停留在几个月前；内部 SOP 散落在无数个语雀文档里，从没整理进系统。

把依赖的数据彻底整理一遍（补全缺失、修正过时、统一格式和标签），并设置官方文档更新后第一时间同步到 GitHub 仓库作为知识库后，效果立刻好了。

**作者的反思**：犯的错不是技术选型错误，而是**问题诊断错误**。AI 做得不好，根因不在模型层，而在数据层。

### 2.2 唱唱反调：哪些场景根本不需要 Agent

很多需求看起来「很 AI」，但用更简单的方案就能解决，而且更好。三类典型（教程原话）：

| 场景 | 例子 | 为什么不需要 Agent |
| --- | --- | --- |
| 固定答案的 FAQ | 「退款政策是什么？」「Wi-Fi 密码多少？」 | 答案固定、明确、不需要推理，FAQ 页面永远不会幻觉，Agent 可能会 |
| 结构化数据查询 | 「上个月 GMV 多少？」「日活趋势？」 | 一条 SQL 或一个数据看板就搞定，用 Agent 反而多了出错环节 |
| 对准确性零容忍的计算 | 「发票含税金额」「贷款月还款额」 | 大模型不是计算器，用公式或程序更可靠 |

一句大白话（教程原话）：**用 Agent 来做加减乘除，就像雇一个大学教授来帮你查字典——能做，但为什么？**

判断关键：查询的意图是**精确的还是模糊的**？精确的就别用 Agent，模糊的才回到 Agent 的甜区。

### 2.3 三维度可行性评估

根据 F2 的公式 `AI Agent 能力上限 = 模型能力 × 数据质量 + 流程编排`，是否适合做 Agent 也对应三个因子（教程原话）：

| 维度 | 核心问题 | 地位 |
| --- | --- | --- |
| 数据可得性 | Agent 要用的数据存在吗？ | 最重要、最容易被低估、最容易在立项阶段验证 |
| 任务可定义性 | 怎么算做对了？ | 决定了你能不能衡量成功 |
| 流程编排选择 | 完全自主 Agent，还是设计好流程的 Workflow？ | 最能体现架构判断力 |

#### 维度一：数据可得性（最关键）

Agent 不是凭空变答案的——要么检索知识库，要么调工具，要么靠对话历史。背后的前提是：**它需要的数据得存在**。

要问的具体问题：

- **内容覆盖**：Agent 需要回答的问题，答案数据存在吗？在数据库里、文档里，还是只在某个老员工脑袋里？
- **数据质量**：数据存在，但准确吗？是不是几个月前的版本？
- **可接入性**：数据存在且准确，但 Agent 能拿到吗？是不是锁在没 API 的系统里？

**一个简单的验证方法（教程原话）**：立项会上随机列 10 个期望 Agent 能回答的典型问题，让团队去找答案数据在哪。如果 10 个里有 6 个找不到，最该做的不是上 Agent，而是先把数据准备好。

#### 维度二：任务可定义性

Agent 做了一件事，你怎么知道它做对了？传统软件是「输入确定、输出确定」，但 LLM 是**概率生成**的，输出不是确定的，是概率分布的采样。

同一个「查物流」问题，LLM 可能返回三种不同表述：
- 「您的订单正在运输中，预计明天送达。」
- 「包裹已在路上，明天到。」
- 「物流状态：运输中，预计送达时间：2026-03-28。」

哪个算对？这就是 LLM 带来的新问题。

任务可定义性要回答两个问题：

1. **输出形式的边界在哪？** —— 哪些表述可接受，哪些算错？
2. **事实正确性怎么验证？** —— 模型可能幻觉，你的验证机制是什么？

关键区别：**有「事实锚点」的任务**（物流系统、用户反馈原文）可以用事实正确性作底线；**没有事实锚点的任务**（写营销文案、分析竞争优势）需要建立主观评估机制（多人打分、A/B 测试）。

实用建议（教程原话）：对于难定义的任务，先用小样本人工评估建立基线——让团队人工写 10 个文案作为「合格线」，再让 Agent 生成 10 个盲测对比。

#### 维度三：流程编排选择（Agent vs Workflow）

| | Agent（自主代理） | Workflow（工作流） |
| --- | --- | --- |
| 控制权 | AI 掌握，人可以中途干预但不必须 | 人掌握，AI 是流程中的智能组件 |
| 特点 | 用户给模糊目标，AI 自己决定怎么做 | 人设计好每一步的输入输出，AI 负责其中需要智能的环节 |
| 优势 | 灵活，能处理设计时没想到的情况 | 可控，每一步输入输出都设计好，出错容易定位 |
| 风险 | 可能做出设计时没想到的错事 | 灵活性差 |

判断用 Agent 还是 Workflow，问三个问题（教程原话）：

1. **数据可得性如何？** —— Agent 需要自己能检索到全部数据；Workflow 可以把数据需求拆到每个步骤，对数据层要求更低。
2. **任务的确定性高吗？** —— 步骤确定可预测 → Workflow；每步都要根据上下文判断 → Agent。
3. **错误的代价是什么？** —— 代价高（资金、法律、医疗）→ 优先 Workflow，把 AI 放在风险可控的环节。

**光谱模型**（不是二元选择）：

```
完全自主 Agent（AI 控制） ←→ 人机协作 Workflow（混合控制） ←→ 传统软件（人控制）
```

三种中间形态：
- **Copilot 模式**：人主导，AI 辅助（如 GitHub Copilot）
- **Human-in-the-loop**：AI 执行，人审核（如客服助手——AI 生成回复，人确认后发送）
- **混合模式**：简单情况 AI 自主，复杂情况升级人工（如退款助手——小额自动批，大额转人工）

> **教程原话**：如果你的团队是第一次做 AI 项目，优先选 Workflow，不要选 Agent。先把 Workflow 跑通，验证 AI 在这个场景中的价值，再逐步增加自主性。「先 Workflow，再 Agent」是更稳妥的路径。

三个维度的关系（教程原话）：**数据可得性是地基，任务可定义性决定能不能衡量成功，流程编排选择决定可控性。** 理想的第一个 AI 项目：数据可得性高、任务可定义性高、流程可控性高。

### 2.4 评估 Checklist（可直接用）

**一、场景匹配度**

| 检查项 | 是 | 否 |
| --- | --- | --- |
| 用户意图是否可能模糊或多样化？ | ☑ | ☐ |
| 回答是否需要从多个数据来源组合信息？ | ☑ | ☐ |
| 任务是否涉及多轮交互？ | ☑ | ☐ |
| 这个任务能否用 if-else 逻辑完整描述？（能 → Agent 过度设计） | ☐ | ☑ |

判断：前三项至少命中一个「是」，且第四项为「否」，才值得考虑 Agent。

**二、数据可得性（最关键）**

| 检查项 | 状态 |
| --- | --- |
| 典型问题的答案数据是否存在？ | 存在 / 部分 / 不存在 |
| 数据是最新的吗？ | 最新 / 有些过时 / 严重过时 |
| 数据格式可被系统处理吗？ | 可处理 / 需转换 / 不可处理 |
| Agent 有技术途径获取吗？ | 可接入 / 需开发 / 无法接入 |
| 用 10 个典型问题测试，能找到几个答案数据？ | __/10 |

判断：超过一半找不到答案数据 → 先建数据，再做 AI。

**三、任务可定义性**

| 检查项 | 状态 |
| --- | --- |
| 能否用一句话描述「做对了」的标准？ | 能 / 模糊 / 不能 |
| 是否有现成的评估数据？ | 有 / 少量 / 没有 |
| 评估标准是客观的还是主观的？ | 客观 / 混合 / 主观 |

**四、流程编排选择**

| 检查项 | 状态 |
| --- | --- |
| 大部分步骤是确定的、可预测的吗？ | 是 / 部分 / 否 |
| AI 做出设计外决策的后果？ | 可接受 / 需审核 / 不可接受 |
| 需要调用多个系统的 API 吗？ | 是（Workflow 更合适）/ 否 |
| 首选 Agent 还是 Workflow？ | Agent / Workflow / 混合 |

**综合建议**

| 评估结果 | 建议 |
| --- | --- |
| 场景匹配 ✓，数据 ✓，任务可定义 ✓，适合 Workflow ✓ | **立即启动**——理想的 AI 项目 |
| 场景匹配 ✓，但数据不足 | **先建数据，再做 AI** |
| 场景匹配 ✓，但任务不可定义 | **先做用户调研**——没有成功标准容易改到天荒地老 |
| 场景匹配 ✓，但该用 Workflow 却选了 Agent | **重新设计流程**——把控制权收回来 |
| 场景不匹配 | **用更简单的方案**——FAQ、看板、脚本 |

### 2.5 Agent 的三个甜区

不是所有问题都适合 Agent，但有三类场景 Agent 最能发挥价值（教程原话）：

| 甜区 | 说明 | 例子 |
| --- | --- | --- |
| 语义理解 | 用户说不清楚要什么，需要 AI 理解和拆解 | 「我下个月去美国出差要办什么手续」——签证？审批？报销？取决于国籍、职级、目的 |
| 工具调用 | 需要调用外部工具/API 才能真正解决问题 | 查数据库、调接口、执行操作 |
| 持续交互 | 任务复杂，需要多轮沟通逐步澄清 | 反复沟通、基于前面结论继续推进 |

**同时命中两个甚至三个甜区**，大概率值得用 Agent。

### 2.6 延伸：本地 Agent 与数据隐私

一个值得提前关注的产品决策：**Agent 应该运行在哪里？**

传统是云端 SaaS，但 2025 年底开始出现**本地 Agent** 趋势，代表是 [OpenClaw](https://github.com/openclaw/openclaw)——完全在用户本地设备运行，数据不出本地。

从产品决策角度，本地 Agent 解决的核心问题是**数据隐私与信任**：做企业内部财务助手，要查报销、预算、合同——如果跑在公有云上，需要把敏感数据传给第三方，很多领导这一步就叫停了。本地 Agent 只「借」一个推理核心，数据本身不出公司网络。

> **教程原话**：当目标用户对数据隐私极度敏感（金融、医疗、法律、企业内部），本地 Agent 可能不是技术选型问题，而是**市场准入**问题。

## 三、D1：用代码控制 AI——从 ChatGPT 到 API

### 3.1 对话的本质是一个消息列表

你在 ChatGPT 网页上聊天，背后非常简单：每一句话和每一句回复，都被组织成一个**消息列表**（messages array），整个列表一起发给模型。

**模型并不「记得」之前说了什么**——它每次收到的都是一个完整的消息列表，然后基于列表生成下一条回复。所谓「多轮对话」，不过是每次把历史消息重新发一遍。

每条消息两个核心字段：**角色（role）** 和 **内容（content）**。

| 角色 | 含义 | 类比 |
| --- | --- | --- |
| `system` | 给模型的「人设说明」——你是谁、该怎么做 | 新同事第一天入职指南 |
| `user` | 用户说的话 | 客户的提问 |
| `assistant` | 模型的回复 | 你给出的回答 |

**System Prompt 是控制 Agent 行为的核心杠杆**——回答用中文还是英文、语气正式还是轻松、不确定时坦诚说不知道还是硬猜，都在 System Prompt 里控制。它本质上就是 F2 讲过的「程序记忆」的载体。

课程用 **LangChain** 框架（`langchain-openai`），基础调用：

```python
from langchain.chat_models import init_chat_model

llm = init_chat_model(
    "tencent/Hunyuan-MT-7B",
    model_provider="openai",  # 通过 OpenAI 兼容接口调用
    base_url="https://api.siliconflow.cn/v1",
    api_key="YOUR_API_KEY",
)

response = llm.invoke([
    ("system", "你是一个简洁高效的技术助手。用中文回答，尽量用一两句话。"),
    ("user", "什么是 RAG？"),
])

print(response.content)
```

多轮对话就是把历史消息追加到列表里再发一次：

```python
messages = [
    ("system", "你是一个简洁高效的技术助手。"),
    ("user", "什么是 RAG？"),
    ("assistant", "RAG 是检索增强生成，先从知识库检索相关内容，再让模型基于这些内容生成回答。"),
    ("user", "它和直接把文档塞进 Prompt 有什么区别？"),
]

response = llm.invoke(messages)
print(response.content)
```

我的理解：这段代码正好印证了 F1 说的「大模型天生没有记忆」。模型没有记忆，对话历史全靠你自己维护列表——这就是上下文窗口在工程层面的体现。

### 3.2 流式输出（Streaming）：首 Token 延迟比总生成时间更重要

ChatGPT 网页上 AI 回答是一个字一个字「打」出来的，这就是**流式输出**。

为什么？大模型生成完整回答可能要几秒甚至十几秒。如果干等到最后一个字才显示，用户会觉得系统卡死了。但如果第一个字在 0.3 秒内就出现，即使整段要 10 秒，用户体感完全不同——他在「看 AI 思考」，不是在「等系统响应」。

> **教程原话**：首 Token 延迟（Time to First Token）比总生成时间更重要。

LangChain 里把 `invoke` 换成 `stream` 就行：

```python
for chunk in llm.stream([
    ("system", "你是一个技术助手。"),
    ("user", "用三句话解释什么是向量数据库。"),
]):
    print(chunk.content, end="", flush=True)
```

> **规则**：凡是面向用户的 AI 回答，都应该用 Streaming。生产环境默认用异步 `ainvoke` / `astream`。

### 3.3 Tool Use：今天最重要的部分

#### 一个关键洞察

ChatGPT 是怎么「上网搜索」「生成图片」「执行 Python 代码」的？

**答案是：它自己做不了这些事。** 大模型的能力只有一个——根据输入文本生成输出文本。它不能上网、不能读文件、不能查数据库。它唯一能做的就是说话。

那它怎么「做事」？答案是 **Tool Use**（也叫 Function Calling）。

机制是这样的（教程原话）：

1. 你告诉模型「你有这些工具可以用」（定义工具）
2. 模型分析问题后，不直接回答，而是说「我需要调用某个工具，参数是这些」（声明调用）
3. **你的代码**去执行这个工具调用，拿到结果（执行工具）
4. 你把结果传回给模型（返回结果）
5. 模型基于工具返回的结果，生成最终回答（继续推理）

**关键：模型不执行工具，你的代码执行工具。** 模型是「指挥」，你的代码是「执行者」。模型能调用什么工具、怎么执行、结果怎么处理，完全由你控制。

Tool Use 不是模型的内置功能，而是模型和你代码之间的一个**协作协议**。

#### 为什么说 Tool Use 是 Agent 的分界线

回到 F2 的新员工类比：一个只会说话的新员工充其量是「顾问」；一个能查公司系统、能操作工具的新员工，才是真正能帮你做事的「同事」。

- 没有 Tool Use → 模型只能基于它知道的东西回答 → **聊天机器人**
- 有了 Tool Use → 模型可以决定去查数据库、调 API、执行操作 → **Agent**

F2 讲的 Agent 四大能力——RAG、Memory、Skill、MCP——在工程实现上全部依赖 Tool Use。查知识库 = 模型声明「调用查询工具」，代码执行检索；存记忆 = 模型声明「调用存储工具」，代码写入存储。

> **教程原话**：理解 Tool Use，就理解了 Agent 与外部世界交互的全部机制。

#### 动手：一个完整的 Tool Use 流程

**第一步：定义工具**——用 `@tool` 装饰器写一个普通 Python 函数：

```python
from langchain_core.tools import tool

@tool
def query_knowledge_base(query: str) -> str:
    """从知识库中检索与用户问题相关的内容。当用户的问题涉及产品功能、技术文档、操作指南等需要查阅知识库的场景时使用。"""
    return search_knowledge_base(query)
```

三个要点（教程原话）：
- **函数名**就是工具名称
- **docstring**就是工具描述——模型根据这段描述判断什么时候该用这个工具（极其重要，写不清模型就不知道什么时候调用）
- **参数类型注解**自动转为 JSON Schema——`query: str` 自动识别为字符串参数

**第二步：绑定工具，准备消息**：

```python
from langchain.chat_models import init_chat_model

llm = init_chat_model(
    "deepseek-ai/DeepSeek-V3",
    model_provider="openai",
    base_url="https://api.siliconflow.cn/v1",
    api_key="YOUR_API_KEY",
)

llm_with_tools = llm.bind_tools([query_knowledge_base])

messages = [
    ("system", "你是一个技术文档助手。当用户问及产品相关问题时，请先查询知识库获取准确信息。"),
    ("user", "seekdb 支持哪些检索方式？"),
]
```

`llm.bind_tools()` 把工具绑定到模型，之后每次调用模型都「知道」有哪些工具可用。

模型会判断：用户问「1+1 等于几」直接回答；问「seekdb 支持哪些检索方式」——特定产品功能问题，需要查知识库。于是模型不返回文本，而是返回一个 **tool call**：「我需要调用 `query_knowledge_base`，参数是 `{"query": "seekdb 支持的检索方式"}`」，存在 `response.tool_calls` 里。

**第三步：你的代码执行工具，结果传回模型**：

```python
from langchain_core.messages import ToolMessage

tools_by_name = {
    query_knowledge_base.name: query_knowledge_base,
}
max_rounds = 5
executed_tool_rounds = 0

while True:
    response = llm_with_tools.invoke(messages)
    if not response.tool_calls:
        final_response = response
        break

    if executed_tool_rounds >= max_rounds:
        raise RuntimeError(f"工具调用已达到 {max_rounds} 轮上限")

    messages.append(response)
    for tool_call in response.tool_calls:
        tool = tools_by_name[tool_call["name"]]
        result = tool.invoke(tool_call["args"])
        messages.append(
            ToolMessage(content=result, tool_call_id=tool_call["id"])
        )
    executed_tool_rounds += 1

print(final_response.content)
```

整个流程：

```
用户提问
    ↓
模型分析 → 需要查资料吗？
    ↓ 是                    ↓ 否
返回 tool_call           直接回答
    ↓
你的代码执行工具（查数据库/调API/读文件）
    ↓
结果传回模型
    ↓
模型再次分析 → 还需要调用工具吗？
    ↓ 是                         ↓ 否
返回下一轮 tool_call          生成最终回答
    ↓
回到「你的代码执行工具」
```

真实 Agent 不能假设「一次工具调用后就有答案」，需要循环调用直到模型不再返回 `tool_calls`，同时设最大轮数避免死循环。

> 调试小技巧（教程原话）：如果模型没调用工具而是直接回答了，八成是工具 docstring 写得不够清晰——模型不知道什么时候该用它。

## 四、P1 和 D1 的呼应：道与术

| P1（道）的判断 | D1（术）的对应 |
| --- | --- |
| 数据可得性是地基 | Tool Use 背后是数据层——管道再精良，没水也白搭 |
| 任务可定义性决定衡量成功 | 有事实锚点的任务用事实正确性作底线 |
| 先 Workflow 再 Agent | d1_4/d1_5 手动编排（Workflow）→ d1_6 create_agent（Agent） |
| 模型不执行工具，代码执行工具 | Tool Use 机制：模型声明，代码执行 |

**一句话呼应（教程原话）**：P1 说「90% 的 Agent 功能失败不是模型不行，而是数据不到位」。对应到工程层面就是——Tool Use 的代码你可以写得很漂亮，但如果工具背后的数据层（知识库、记忆系统、外部数据源）没建设好，模型拿到的依然是垃圾数据，回答质量不会好。**代码连接的是管道，数据才是水。**

## 五、我自己的五条体会

以下是我读完后的个人判断，不是教程原文：

1. **「数据在哪」应该写进立项会的固定议程。** 每次讨论 AI 需求，第一个问题不是「用什么模型」，而是「10 个典型问题的答案数据在哪」。这个验证只要半天，能避免几个月弯路。
2. **第一次做 AI 项目，老老实实用 Workflow。** 「先 Workflow 再 Agent」不是保守，是因为 Workflow 在数据层、成功标准、错误控制三方面门槛都更低——先验证价值，再逐步放权。
3. **Tool Use 的 docstring 是产品设计，不是代码注释。** 模型靠这段描述判断「什么时候用这个工具」，写得好不好直接决定 Agent 行为。这和 System Prompt 一样，是控制 Agent 的核心杠杆。
4. **流式输出是用户体验的底线。** 首 Token 延迟比总生成时间重要——这个原则不只适用于 AI，视频也是「边下边播」可接受，「下完再播」不能忍。
5. **Agent 落地的瓶颈在数据层，不在模型层。** 从论坛小助手的故事到 Tool Use 的机制，反复印证同一件事：模型负责推理，数据决定上限。换模型救不了数据缺失。
