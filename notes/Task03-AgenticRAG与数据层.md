## 先给三句话结论

1. **RAG 的 R 是 Retrieval，不是 Vector。** 把 RAG 等同于「向量库 + 相似度搜索 + LLM」是一种早期实现，不是定义；全文、过滤、图谱、API 调用，全都算 R。
2. **传统 RAG 和 Agentic RAG 的差别不是复杂度，而是有没有环。** 前者是一张写死的 DAG，后者允许「搜得不好就回去再搜一次」。
3. **「AI 答得不好」是症状，不是诊断。** 用三层归因框架 + 决策树排查，绝大多数问题会落在数据层，而不是模型层。

## 二、P2：把「AI 答错了」变成一道可以排查的题

### 2.1 第一个误解：RAG 不等于向量搜索

教程原话：RAG 全称是 **Retrieval-Augmented Generation**，重点在第一个词 **Retrieval，检索**。这里的「检索」不是特指向量检索，而是所有能把有用信息取回给模型的手段：

- 全文 / 关键词检索：适合错误码、版本号、产品名、专有名词
- 向量语义检索：适合口语化提问、同义表达、模糊需求
- 标量 / 元数据过滤：按租户、时间、产品线、权限、文档类型做范围筛选
- 图谱 / 关系跳转：适合多跳关系问题
- API 工具调用：查实时状态和结构化数据

课程里给了一个很扎心的真实案例（教程原话）：用户搜「seekdb 1.2.0 版本的兼容性」，纯向量检索返回的却是 **1.0.0 版本**的兼容性文档——因为在向量空间里「1.2.0 的兼容性」和「1.0.0 的兼容性」实在太像了。

课程对此的结论我抄下来：问题不在于「向量检索没用」，而在于**它只是 Retrieval 里的其中一路，不应该独占整个 R**。

我的理解：这句话是整个 Task03 的地基。只要还认为 RAG = 向量搜索，后面的混合搜索、重排、路由都会显得像「高级玩法」；一旦承认 R 是一个工具箱，那些东西就变成了必需品。

### 2.2 传统 RAG vs Agentic RAG：差的是一个「环」

教程原话，用一句话概括：

- 传统 RAG：流程大多是预先设计好的，一般是无环的
- Agentic RAG：流程里开始出现闭环，系统可以自主决定下一步怎么走

很多人以为传统 RAG 就是「提问 → 搜一次 → 取 TopK → 拼 Prompt → 回答」。课程明确纠正了这个印象：成熟的传统 RAG 可以很复杂——query 改写、路由、多路召回、重排、上下文压缩、引用生成、答案后处理都有，但它仍然是一张 **有向无环图（DAG）**，走完就结束。

Agentic RAG 的变化在于，系统在运行时自己判断五件事（教程原话整理）：

| 判断 | 具体问题 |
| --- | --- |
| 要不要检索 | 靠模型常识能答，还是必须查外部资料 |
| 先检索哪一路 | FAQ、文档、数据库、站内搜索，还是直接调工具 |
| 一次够不够 | 结果不理想时，要不要改写 query 补搜第二轮 |
| 要不要多跳 | 当前答案是否依赖前一步结果 |
| 怎么合并证据 | 多来源结果如何重排、去重、归因再交给模型 |

所以结构上的核心差异只有一条：**传统 RAG 通常无环，Agentic RAG 可以有环——可以停下来、回退、重试、补搜、改路由。**

我的理解：用户觉得一个系统「更聪明」，很多时候不是模型变强了，而是流程开始能自我调整了。这解释了为什么「换个 GPT-5 试试」经常没用——你换的是发动机，坏的却是路。

### 2.3 一个完整 RAG 的六段链路

教程原话，一条能上线、能持续优化的 RAG 至少要有六段：

**数据准备（indexing）→ 问题理解与改写（query analysis）→ 搜索召回（retrieval）→ 融合重排（fusion / reranking）→ 回答生成（generation）→ 评估反馈（evaluation）**

前三步决定「能不能找对」，后三步决定「能不能答对」。逐段记要点：

**① 数据准备**（最容易被低估，最影响最终效果）

要回答的问题不是「丢进向量库」，而是：怎么加载、怎么解析、怎么清洗、怎么切分、怎么增强（补标题/章节/别名/版本号/权限/时间等元数据）、怎么建索引、怎么更新。

课程原话：**数据准备，决定了你后面到底有没有资格谈「高质量检索」。** 没有标题结构，语义召回会变差；没有版本号、权限标签，过滤搜索就做不准；chunk 切太碎丢上下文，切太大引噪音。

**② 改写 & 路由**

问题分析、实体抽取（产品名、版本号、错误码、时间范围）、问题改写、问题扩展、问题拆解、HyDE（先生成假想答案再检索）、step-back prompting（先抽象成更高层问题）、路径路由。

本质是：**把「用户语言」翻译成「系统更容易找对信息的语言和路径」。**

**③ 搜索召回**

目标是「尽可能别漏掉可能有用的证据」，而不是直接给答案。做法有：向量召回、全文召回、标量召回、结构化查询（SQL/接口）、多表示召回（先摘要后原文）、父子检索（小块命中、大块补上下文）。这一步偏「广撒网」。

**④ 融合 & 重排**

结果融合、去重、chunk 合并、重排序（按真实相关性而非初始召回分数）、RRF 融合排序、可信度加权（来源权威性/时间/权限）、上下文压缩。

课程原话：很多系统效果差，不是「没搜到」，而是**搜到了但排序出了问题**。

**⑤ 上下文组织与生成**

上下文组装（按主题分组、按时间排序、按子任务拆分）、证据引用、约束生成（信息不足就说不知道）、结构化输出、后处理。

**⑥ 评估与反馈闭环**

过程评估、节点评估、结果评估、来源分析、闭环优化。课程原话：RAG 不是答完就结束，而是一条能持续调优的链路；任何一环做差了，最后都会表现成同一句话——「AI 没能解决我的问题」。

### 2.4 常见增强节点：Naive / Query Rewrite / CRAG / Self-RAG

课程用一个小节把「在标准流程上插节点」讲清楚了（教程原话整理）：

| 形态 | 核心思想 | 插在哪 |
| --- | --- | --- |
| Naive RAG | 搜一次、取 TopK、拼 Prompt | 无 |
| Query Rewrite RAG | 先让模型把问题改写成更适合搜索的 query | 流程最前面 |
| CRAG（Corrective RAG） | 检索后、生成前先判断这批证据值不值得用，不够好就纠错重搜 | 召回之后 |
| Self-RAG | 把「要不要检索、够不够、有没有证据支撑」部分内化到模型自己身上，边生成边自我检查 | 全程 |

CRAG 的判断分三档：Correct（直接用）、Ambiguous（补充搜索后合并）、Incorrect（换网络搜索重新生成）。Self-RAG 则在流程里加了 `Retrieve?`、`IsRel?`、`IsSup?`、`IsUse?` 四个自检点。

课程对这四个形态的总结我觉得值得抄：**RAG 的演进，不只是「换一个更强的检索器」，而是在标准流程的不同位置上，不断插入新的判断节点、修正节点和反馈节点。**

### 2.5 评估：RAGAS 四指标正好对上四个阶段

教程原话：评估这一层如果没有，你就不知道系统是「搜漏了」「搜偏了」「排错了」「答编了」还是「答得不贴题」。

| 指标 | 对应阶段 | 在问什么 |
| --- | --- | --- |
| 上下文召回率（Context Recall） | 搜索召回 | 该召回的证据有没有被召回来 |
| 上下文精确度（Context Precision） | 融合重排 | 召回内容里有多少真正相关，多少是噪音 |
| 忠实度（Faithfulness） | 生成 | 回答是否忠于给定上下文，有没有编造 |
| 答案相关性（Answer Relevancy） | 回答用户 | 回答是否真正回答了用户问题 |

四个指标低分别指向不同病根：Recall 低 → 数据覆盖/数据准备/query 改写/检索策略；Precision 低 → 噪音太多、重排或过滤不够；Faithfulness 低 → 幻觉、Prompt 约束不足、引用设计不够；Relevancy 低 → 问题理解错了，或没围绕用户意图组织答案。

我的理解：这套指标最大的价值不是「四个名词」，而是它把「AI 怎么感觉不太行」这种主观吐槽，切成四个可以做实验、可以对比的数值。谁低就查谁，不用猜。

### 2.6 三层归因框架：大多数问题在数据层

这是 P2 最重要的部分。课程先用医生类比：头疼是**症状**，不是**诊断**；直接开止疼药可能掩盖高血压。「AI 答得不好」就是那个头疼。

三层归因（教程原话整理）：

| 层 | 表现 | 根因 | 解法 |
| --- | --- | --- | --- |
| 数据层 A：检索不到 | 知识库里压根没有，或有但没清洗/切好/打标/同步，实际「不可检索」 | 内容覆盖或数据准备 | 补知识库、重做数据准备（首先是产品决策） |
| 数据层 B：检索到错的 | 有正确答案，但返回不相关、太浅、太偏、排太后 | 检索相关性或检索路径设计 | 升级混合搜索、优化分块/重排/改写 |
| 模型层：答案无中生有 | 检索到了也对，但模型添油加醋 | 模型幻觉 | 引用来源设计 + 约束生成 |
| 业务层：答对但不合适 | 事实正确，但风格/合规/场景不对 | 回答风格或业务规则不匹配 | 优化 System Prompt、补业务规则 |

课程给了明确的实践比例（教程原话）：**60% 到 80% 的「AI 答错了」其实是「知识库没覆盖」或「检索到了不相关的内容」；真正属于模型幻觉的通常只有 10% 到 20%；业务层占剩下更少的部分。**

而 PM 最常见的反应是「换个更好的模型」——这在课程里被直接称为**误诊**。

### 2.7 归因决策树：四步定位

```
第一步：还原现场，判断不对的类型
├── C. 事实没问题，但不合规 / 风格不适合 → 业务层（查 Prompt 与业务规则）
└── A 或 B → 继续第二步

第二步：手动去知识库搜，有没有正确答案？
├── 没有 → 数据层·内容覆盖（补知识库）
└── 有 → 继续第三步

第三步：看这次回答实际检索到了什么？
├── 不是正确内容（不相关 / 排太后） → 数据层·检索策略（混合搜索等）
└── 是正确内容 → 继续第四步

第四步：模型有没有正确使用这些内容？
├── 添加了编造信息 → 模型层·幻觉（引用设计 + 约束生成）
└── 没有充分利用 → 查 Prompt 是否有效引导
```

课程还配了一张「交给工程同学」的交接表，把 PM 的判断对应到 D2/D3 的最小验收证据：

| P2 定位到的问题 | 对应实战 | 最小验收证据 |
| --- | --- | --- |
| 文档切分或元数据不完整 | D2 数据准备 | 固定案例能召回完整上下文，版本/来源/权限可过滤 |
| 精确标识符召回错误 | D2 / D3 混合检索 | 错误码、版本号、季度、函数名进入 Top-3 |
| 多路结果重复或冲突 | D3 融合重排 | 文档 ID 去重，权限先过滤，规则可解释 |
| 回答脱离检索证据 | D3 引用校验 | 每个引用都来自本次上下文，未知引用触发重试或拒答 |
| 不知道优化是否有效 | D3 离线评测 | 固定回归集输出 Hit@1、Hit@3、MRR、召回率、拒答与调用量 |

我的理解：这张表的价值在于把「产品觉得不好」和「工程觉得做完了」拉到同一个完成标准上。没有验收证据的优化，最后都会变成「感觉好像好了一点」。

## 三、D2：桥对面到底放什么数据库

D2 的结构很清楚：先把数据准备好（切分 + 向量化），再回答「用什么库、怎么查」。

### 3.1 切分：把长文档变成可检索的片段

为什么要切？教程原话给了两个理由：整篇文档向量化，语义会被「稀释」（一个向量代表不了所有话题）；检索命中后把几千字全塞给模型，浪费 Token 还干扰注意力。

基础做法是固定大小 + 固定 overlap。课程给了四条实用原则：按语义边界切、片段别太长（500~800 字是常见范围）、保留 50~100 字重叠、保留元数据（来源、章节、更新时间）。

进阶有三种策略，课程用同一个「数据库运维手册」语料做了 d2_5 对比实验（Recall@3，四种策略都跑出 80% 量级，说明要放大数据量才能看出差异）：

**策略一：语义分块（Semantic Chunking）**

先按句切，每句算 Embedding，比较相邻句余弦相似度，在「异常下跌」处插断点。关键在于「异常」怎么定：写死阈值会因文档类型不同而失效，更稳妥的是 **percentile 阈值（默认 95 分位，常在 90–95 之间微调）**——阈值跟着当前文档自己的分布走。

代价（教程原话）：入库时每句都要调用一次 Embedding API，500 页文档可能产生数万次调用。收益是话题频繁切换的散文、新闻、会议纪要上通常有 **2–5 个点**的 Recall 提升。

**策略二：动态 Overlap（Dynamic Overlap）**

核心假设是：文档每个位置的「边界风险」不一样。同质段落内部用较小 overlap（如 10%），段落边界/标题行附近用较大 overlap（如 25–30%），代码块、表格前后适当加大。

课程引用 Yoke Agent 的实验（教程原话）：在 512 token 分块上仅增加 64 token 的 overlap，Recall 提升约 **4 个百分点**，与换用更大 Embedding 模型同量级，但**入库成本几乎为零**。所以这是三种策略里**性价比最高**的升级路径。

**策略三：父子 Chunk（Parent-Child / Small-to-Big）**

解决的是「小块检索准但上下文不够，大块上下文够但语义被稀释」的矛盾。做法是**把索引粒度和返回粒度解耦**：父 chunk（如 500 字）存 docstore 不建索引，子 chunk（如 120 字）建向量索引；查询时用子块命中，取 parent_id 返回父块给 LLM。

课程给的收益数字：答案完整度普遍提升 **15–30%**，代价是 LLM 侧 token 消耗随父块大小增加。LangChain 的 `ParentDocumentRetriever`、LlamaIndex 的 `HierarchicalNodeParser` + `AutoMergingRetriever` 都是这条路。

**怎么选**（课程决策表，摘几条）：刚起步/文档量小用固定 overlap；Markdown/API 文档按标题预切 + 固定 overlap；边界处常丢上下文用动态 overlap；话题跳跃的无结构长文用语义分块；检索准但 LLM 答不全用父子 chunk；多种文档类型混合就按类型路由不同策略。

课程那句我觉得最实用：chunk 策略、chunk 大小、overlap 和 Embedding 模型一样，都值得在**自己的数据**上试出来——拿 20–50 条真实 query 跑一轮 Recall@K，比看任何排行榜都靠谱。

### 3.2 向量化与 Embedding 选型：四维度 + 五个坑

向量化本身没门槛：调一次 Embedding API，把文字变成一串浮点数。真正的难题是「模型那么多，选哪个」。

**先搞懂两个评测概念**

- **MTEB 排行榜**：最权威的公开评测，但主要测纯文本短文本，不覆盖多模态、跨语言、MRL 降维、长文档大海捞针。适合**缩小候选范围**，不能替代实测。
- **Recall@K 对比**：拿 20–50 条真实业务查询 + 标注 Ground Truth，看正确答案出现在前 K 条的比例。50 条里 42 条在 Top-3，就是 Recall@3 = 84%。通常同时看 Recall@1、Recall@5 和 MRR。

**四个核心维度**

| 维度 | 关键判断（教程原话整理） |
| --- | --- |
| 中英文能力 | 中文为主选 `bge-m3` / `bge-large-zh-v1.5` / 通义系列；英文或出海选 `text-embedding-3-large` / Gemini / Voyage；chunk 超 500 字要选 8192 token 以上的模型，`bge-large-zh-v1.5` 只有 512 tokens 会截断 |
| 多模态支持 | 纯文本 `bge-m3` 够用；图表/扫描件密集再上 ColPali 式页面级多向量，或 `Qwen3-VL-Embedding` 统一向量；注意「模态间隙」指标。**多模态 Embedding 不能替代混合搜索**，精确匹配仍要全文兜底 |
| 成本 | 学习原型用硅基流动免费 `bge-m3`（¥0）；月调用 < 500 万 token 不建议自建 GPU；> 5000 万 token 或数据不能出内网再评估自部署（约 ¥500–2000/月）；向量维度直接影响存储：1024 维约 4 KB/条，100 万条约 4 GB |
| 延迟 | 在线实时查询选 600M 参数以下（`bge-m3` 单条 50–150 ms）；离线批量入库可以用 `Qwen3-Embedding-8B`；海外 API 国内调用通常多 80–200 ms 网络开销 |

课程默认选 `bge-m3`（免费、中英文均衡、1024 维、8192 token、单条 50–150 ms），理由是它在四个维度上取得了最好的**学习体验平衡**——但明确说了这不是生产环境的最优解。

**五个容易被忽略的工程细节**（我觉得这段最值钱）

1. **入库和查询必须用同一个模型。** 换模型意味着全量 re-index，否则两个向量空间不一致，检索断崖式下降。
2. **查询和文档的编码方式可能不同。** `bge-m3` 编码查询要加检索前缀（`prompt_name="query"`），编码文档不加；Jina 用 `task="retrieval.query"` / `retrieval.passage` 区分。这不是可选项，是模型训练时设计好的用法。
3. **`bge-m3` 自带三种检索模式**：稠密向量、稀疏向量（类似 BM25）、多向量（ColBERT 风格）。一个模型就能做 Embedding 层的混合检索。
4. **Embedding 负责初筛，Reranker 负责精排。** 工业级架构是 Embedding 召回 Top-50~100，再用 `bge-reranker-v2-m3` 精排到 Top-10。课程给的实测数字：加 Reranker 后准确率从 **78% 提升到 91%**。
5. **缓存和批量处理能省 80% 的成本。** 文本哈希做缓存 key，批量入库一次传几十上百条。

### 3.3 传统数据库为什么不够用

教程原话：MySQL、PostgreSQL、MongoDB 的设计哲学都是**精确匹配**——你告诉它 id=123，它帮你找到；前提是「你知道你要找什么，而且能精确描述它」。

但 AI 应用里用户说的是：「我们上个月讨论过的那个性能优化方案是什么？」「有没有关于用户权限设计的最佳实践？」用户不知道文档 ID，不知道标题措辞，甚至不知道那份文档叫什么——他只知道「大概是关于什么的」。

**传统数据库做精确匹配，AI 应用需要语义匹配**——这是根本错位，你没法写一条 SQL 来「找意思最接近的段落」。

### 3.4 向量搜索的软肋：懂语义，不懂精确

课程用错误码举例：用户搜「错误码 E-4012 的解决方案」，纯向量搜索返回了 E-4011、E-4013、E-4010——因为在向量空间里它们几乎一样近。

这不是个例，课程列了一整张表：产品型号 `OB-4.2.1` 可能返回 3.x；API 参数 `max_retries` 可能返回 `retry_count`；版本号 `v2.3.1` 可能返回 v2.3.0；配置项 `enable_ssl_verify` 可能返回 SSL 通用讨论；「超时 30 秒」可能返回「超时 60 秒」。

规律：**凡是需要精确匹配的内容——专有名词、型号编号、版本号、配置项名、精确数值——向量搜索都不可靠。** 因为 Embedding 学到的是语义，不是字面。

课程那句定性很重要：**这不是一个模型问题，是一个搜索策略问题。**

### 3.5 混合搜索：三种能力缺一不可

| 能力 | 负责什么 |
| --- | --- |
| 向量搜索 | 「找意思最接近的内容」 |
| 全文搜索 | 「找包含这个确切词的内容」 |
| 关系过滤 | 「只在最近更新的文档中找」「只在产品 A 的文档中找」 |

课程用两个查询做对照：搜「错误码 E-4012」时，纯向量会把 E-4013 排前面，纯全文能精确命中但用户措辞不精确就找不到，混合搜索两者兼得；搜「怎么优化数据库查询性能」时，纯全文只能找到字面包含这几个字的文档，会漏掉「查询优化」「索引设计」「执行计划分析」。

课程结论：**这不是「哪个更好」的选择题，是「两种能力分别覆盖不同场景」的工程现实。任何只用其中一种的方案，都有明显的盲区。**

### 3.6 三个厨房 vs 一个厨房

实现混合搜索最常见的方式是拼三个系统：向量库（Pinecone/Milvus）+ 搜索引擎（Elasticsearch）+ 关系库（PostgreSQL），再在应用层写胶水代码合并结果。

课程用「三个厨房」类比说明为什么这不是好方案：冷菜在一楼、热菜在二楼、甜点在三楼，各有各的仓库和库存系统。每来一位客人，订单要拆三份、有人跑上跑下对进度、最后凑成一桌；客人说「冷菜不要香菜」，你还得确保这话传到了冷菜厨房。

对应到系统就是：三套部署、三套运维、三套 API、三个数据同步流程；同一份文档要在三个系统保持一致；一个系统用相关性分数排序、一个用 BM25、一个用时间，你怎么合成统一排名。

课程给的解法是「一个厨房，所有菜都能做」：**一个引擎天生就能同时处理向量数据、全文数据和关系数据**，查询时一条语句同时执行语义搜索、关键词搜索和结构化过滤，结果在引擎内部融合。课程有句话我记下了：**你做得对的方式也恰好是最简单的方式。**

（课程此处介绍的是 seekdb，AI 原生混合搜索数据库。我把它理解为「把胶水层下沉到引擎里」的一种产品形态，不是唯一选择——但判断标准是一样的：能不能在一条查询里同时做三件事。）

### 3.7 五分钟跑通：对比实验说明「对和错」

课程给了最小可运行示例（`pip install pyseekdb` → 建集合时同时声明向量索引和全文索引 → 写入 5 条文档 → `hybrid_search`），并展示两种查询：

- 查「错误码 E-4012 的解决方案」：E-4012 被精确排第一，因为全文精确匹配了关键词，和向量分数一起参与排序。
- 查「怎么设计用户权限」：「访问控制架构设计」被找到，尽管两者没有共同关键词——这是向量搜索的功劳。

对比实验的结果（教程原话整理）：

| 排名 | 纯向量搜索 | 混合搜索 |
| --- | --- | --- |
| 1 | E-4013 认证失败（语义最近） | **E-4012 连接超时（精确命中）** |
| 2 | E-4012 连接超时 | E-4013 认证失败（语义补充） |
| 3 | 查询性能优化（也沾点边） | OB-4.2.1 版本新特性 |

课程对这件事的定性我完全认同：**一个错误码搞错，如果结果直接被 Agent 用来回答用户，用户得到的就是错误的解决方案。这不是「效果差一点」，是「对和错」的问题。**

## 四、道与术怎么对上

把 P2 和 D2 叠在一起看，对应关系其实非常整齐：

| P2 的判断 | D2 的落地 |
| --- | --- |
| RAG 的 R 是 Retrieval，不是 Vector | 混合搜索：向量 + 全文 + 关系过滤 |
| 六段链路的第一段「数据准备」决定检索上限 | 切分四策略 + 元数据 + 向量化选型 |
| 检索到了错的内容 → 数据层·检索策略 | 纯向量 vs 混合搜索的对比实验 |
| 大多数问题在数据层（60%~80%） | Embedding 选型、分块、reranker 都属数据层投入 |
| 混合搜索是流程底座 | 「三个厨房 → 一个厨房」，复杂度内置到引擎 |

课程也划清了边界：P2 定义问题、链路和验收口径；D2 打牢数据准备和多路检索；D3 再补动态路由、引用校验、失败重试和 60 条离线评测。

我的理解：这三篇其实是一条流水线——P2 负责「知道该治什么病」，D2 负责「把药做出来」，D3 负责「验药效」。跳过任何一步，最后都会退化成「感觉好像好一点」。

## 五、我自己的五条体会

以下是我读完后的个人判断，不是教程原文：

1. **「R 是不是做对了」应该写进 AI 产品的复盘模板。** 归因决策树四步里，前三步全在查数据层，只有第四步才轮到模型。这个顺序本身就是一种产品纪律——先排除最容易犯的错，再怀疑最难改的东西。
2. **「换个更强的模型」是最贵的偷懒。** 课程给的 60%~80% 数字很刺眼：大部分预算花在了 10%~20% 的问题上。评估模型、切 API、调参数的沉没成本，比老老实实做一次混合搜索高得多。
3. **切分策略里最该先做的是动态 overlap，不是语义分块。** 语义分块听起来高级，但每句一次 Embedding 的入库成本是实打实的；动态 overlap 只改重叠量，几乎零成本就能补边界召回。先摘低垂果实。
4. **Embedding 的两个「同模型」细节，是那种不踩一次不会信的坑。** 入库和查询用不同模型、查询不加检索前缀——这两个错误不会报错，只会让效果莫名其妙地差，而且很难归因。这类「静默失败」比崩溃更危险。
5. **混合搜索不是优化项，是及格线。** 只要知识库里有版本号、错误码、配置项名，纯向量检索就一定会出错，而且是「对和错」级别的错。这和模型强弱无关，是方法论边界。
